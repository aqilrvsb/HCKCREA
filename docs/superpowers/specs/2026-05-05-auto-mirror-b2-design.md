# Auto-Mirror Generated Media to B2 — Design

**Date:** 2026-05-05
**Status:** Approved (Path A)
**Author:** Brainstormed with admin@gmail.com on production peninglab.com
**Hypothesis test (Phase 0):** ✅ Passed — browser HTTP cache works on stable B2 URLs (verified via MCP Playwright)

---

## Goal

Eliminate video/image re-streaming on every view. After this lands, opening any history card a second time (refresh, next session, next day, next week) plays/displays from the user's local browser disk cache with **zero network bytes** and instant paint. First-time views go directly to B2 (Cloudflare CDN can be added later as a pure perf upgrade with no code change).

| Metric | Today | After this lands |
|---|---|---|
| Refresh same video | Re-streams (~5-30MB, 2-4s) | **0 bytes, instant** |
| Open same video next day | Re-streams (~5-30MB, 2-4s) | **0 bytes, instant** |
| Open on second device | Re-streams (~5-30MB, 2-4s) | First view streams once (~500ms), then cached forever |
| Console QUIC errors from `fal.media`/`v3b.fal.media` | Frequent | Gone (we don't serve fal URLs anymore) |
| Save flow latency | 5-30s (downloads + uploads) | <100ms (just flag flip) |

Every video and image generated by the SaaS — across UGC, Auto Content, Cinema, Storytelling videos, Storytelling scene images, and the Image tab — is auto-mirrored to a single public B2 bucket at generation time. The user-facing UI (validity badge, Save button, Storage section, 1024MB quota) stays exactly as it is today.

## Non-goals (out of scope for this spec)

- Cloudflare CDN setup — Phase 2, pure additive perf upgrade, env-var swap from `https://f005.backblazeb2.com/file/peninglab-content` to `https://cdn.peninglab.com`
- Cross-device cache sync (account-level pre-warming) — separate project
- JPG poster extraction (TikTok-style instant grid) — separate spec, can layer on later
- Removing the existing `peninglab-storage` private bucket / current Save flow's storage table — this spec coexists alongside; no destructive migration
- Re-architecting `<video>` lazy-load behavior — the existing `LazyVideo` token bucket stays as-is
- Changing the 14-day TTL UX or removing the "Save" button — UX unchanged

## Component 1 — `peninglab-content` public bucket

| Property | Value |
|---|---|
| Name | `peninglab-content` |
| Endpoint | `s3.us-east-005.backblazeb2.com` |
| Type | Public (read-anonymous) |
| Encryption | SSE-B2 (default, free, transparent) |
| Object Lock | Disabled (cleanup needs delete capability) |
| Lifecycle | Keep all versions (Modal cron handles deletion) |
| App Key | `peninglab-content-key`, scoped to this bucket only, Read+Write |

### Object key convention

```
users/{userId}/{type}/{historyId}.{ext}
```

Where:
- `userId` = Supabase `auth.users.id` UUID
- `type` ∈ {`image`, `video`, `auto`, `cinema`, `seedance`, `fairytale`, `fairytale-scene`, `clone`}
- `historyId` = `history.id` UUID
- `ext` = `mp4` for videos, `png`/`jpg` for images

### Public URL pattern (the value of `B2_CONTENT_PUBLIC_BASE`)

```
https://f005.backblazeb2.com/file/peninglab-content/users/{userId}/{type}/{historyId}.{ext}
```

This is stored verbatim in `history.output_url` after a successful mirror.

### Env vars (already configured on Vercel by user)

```
B2_CONTENT_BUCKET=peninglab-content
B2_CONTENT_KEY_ID=<scoped keyID>
B2_CONTENT_APP_KEY=<scoped applicationKey>
B2_CONTENT_ENDPOINT=https://s3.us-east-005.backblazeb2.com
B2_CONTENT_REGION=us-east-005
B2_CONTENT_PUBLIC_BASE=https://f005.backblazeb2.com/file/peninglab-content
```

## Component 2 — Generation-time mirror

Three different injection points cover all six surfaces:

### 2a. `lib/settle.ts` — UGC, Auto, Cinema, Extend

The existing webhook handler at `lib/settle.ts` is where Crun/RunningHub provider URLs land in `history.output_url`. We hook in BEFORE that update happens:

```ts
// Inside settle's webhook-to-DB path, after provider URL is resolved
//   from { providerUrl, type, historyId, userId, ext }:

const b2Key = buildContentKey({ userId, type, historyId, ext });
const publicUrl = `${process.env.B2_CONTENT_PUBLIC_BASE}/${b2Key}`;

try {
  await mirrorToContentBucket({ providerUrl, key: b2Key, contentType });
  // Success: store the stable B2 public URL, never the provider URL
  await admin.from("history").update({
    status: "done",
    output_url: publicUrl,
    b2_mirrored_at: new Date().toISOString(),
  }).eq("id", historyId);
} catch (mirrorErr) {
  // Mirror failure does NOT fail the gen — fall back to provider URL
  // and a backfill job will retry later. User still sees their video.
  await admin.from("history").update({
    status: "done",
    output_url: providerUrl, // fallback
    error_message: `Mirror to B2 failed: ${String(mirrorErr).slice(0, 200)}`,
  }).eq("id", historyId);
}
```

**Why "best-effort" not "blocking":** if B2 is briefly down, we don't lose the user's generation. They get the video (from provider) and the next-day backfill picks up the un-mirrored row.

### 2b. `app/api/generate/image/route.ts` — Image tab (sync)

Image generation is synchronous (provider returns URL in the response, no webhook). Mirror happens inline:

```ts
// after providerImageUrl is known:
const b2Key = buildContentKey({ userId, type: "image", historyId, ext: "png" });
const publicUrl = `${process.env.B2_CONTENT_PUBLIC_BASE}/${b2Key}`;
try {
  await mirrorToContentBucket({ providerUrl: providerImageUrl, key: b2Key, contentType: "image/png" });
  output_url = publicUrl;
} catch {
  output_url = providerImageUrl; // fallback
}
```

### 2c. `modal_fairytale.py` — Storytelling videos + scene images

Already uploads to B2! Today it uploads to `peninglab-storage` (private). Change the bucket name to `peninglab-content` and the URL it writes back to `history.output_url` to the public URL pattern. ~10-line change in two places (the video upload + the scene image upload).

### 2d. New helper: `lib/mirror-to-b2.ts`

```ts
// Pure helper used by 2a, 2b. Wraps lib/b2.ts uploadFromUrl
// against the new content bucket using B2_CONTENT_* env vars.

export function buildContentKey(opts: {
  userId: string;
  type: string;
  historyId: string;
  ext: string;
}): string { ... }

export async function mirrorToContentBucket(opts: {
  providerUrl: string;
  key: string;
  contentType?: string;
}): Promise<{ key: string; size: number }> { ... }
```

The helper reuses `lib/b2.ts`'s `uploadBuffer` SigV4 implementation but with the content bucket's separate credentials.

## Component 3 — Save flow change

### Today's flow (in `app/api/storage/save/route.ts`)

```
1. Fetch history.output_url (provider URL, 14-day temp)
2. fetch() the file from provider (5-15s, multi-MB download)
3. uploadFromUrl() to peninglab-storage (5-15s, multi-MB upload)
4. signedGetUrl() → 7-day signed URL
5. INSERT storage row { user_id, history_id, type, b2_bucket, b2_key, size_bytes, content_type, source_url, cached_url, cached_url_exp, created_at }
6. Return signed URL to client
```

**Total latency: 10-30s for a video. UX feels slow.**

### New flow (after auto-mirror lands)

```
1. Fetch history.output_url (already a peninglab-content public URL)
2. If output_url is on peninglab-content:
   - HEAD the B2 file to get size_bytes + content_type
   - INSERT storage row pointing to the SAME b2_key in peninglab-content
   - b2_bucket = 'peninglab-content', cached_url = output_url, cached_url_exp = far future (5 years)
   - No download, no upload
3. If output_url is still a provider URL (mirror failed earlier — rare):
   - Fall back to old flow (download + upload to peninglab-storage)
   - This is a graceful degradation path; backfill will eventually fix the row
4. Return cached_url to client
```

**Total latency: <100ms in the common case.**

### Storage table semantics (unchanged)

The `storage` table keeps its purpose: list of files the user has explicitly marked permanent. `/api/storage/list`, `/api/storage/delete`, `/api/storage/status`, the 1024MB quota check — all work as-is. The only difference is `b2_bucket` for new saves is `peninglab-content` (public), and `b2_key` is the same key already used by `history.output_url`.

### Save button UX

The button on the card stays identical. The visible state machine:
- Before save: `🔓 14d` (validity badge counts down)
- After save: `🔒 SAVED` (badge changes; row appears in Storage section)
- After save, file location on B2: **unchanged** — no file move, no URL change, no cache invalidation

## Component 4 — Cleanup cron (Modal, daily)

### What runs

A new Modal worker `modal_b2_cleanup.py` (or extend the existing Modal app — implementation choice). Triggered by Modal scheduler daily at **03:00 MYT (19:00 UTC)** — Malaysia low-traffic window.

```python
# pseudocode
def cleanup_b2_unsaved():
    # Find history rows that:
    #   - were mirrored to peninglab-content (have b2_mirrored_at)
    #   - are older than 14 days
    #   - have NO matching storage row (i.e., user did not Save)
    rows = supabase.rpc("history_unsaved_past_ttl")
    
    for row in rows:
        b2_key = derive_key_from_output_url(row.output_url)
        try:
            b2_delete(bucket="peninglab-content", key=b2_key)
            # Don't delete the history row — UI already hides it via TTL filter.
            # Just clear b2_mirrored_at so the cleanup is idempotent.
            supabase.update("history").set({ b2_mirrored_at: None }).eq("id", row.id)
        except Exception as e:
            log.warn(f"cleanup failed for {row.id}: {e}")
            continue
```

The DB function `history_unsaved_past_ttl()` (added in this spec's migration):

```sql
CREATE OR REPLACE FUNCTION history_unsaved_past_ttl()
RETURNS TABLE (
  id UUID,
  user_id UUID,
  type TEXT,
  output_url TEXT,
  b2_mirrored_at TIMESTAMPTZ
)
LANGUAGE SQL
SECURITY DEFINER
AS $$
  SELECT h.id, h.user_id, h.type, h.output_url, h.b2_mirrored_at
  FROM history h
  WHERE h.b2_mirrored_at IS NOT NULL
    AND h.created_at < NOW() - INTERVAL '14 days'
    AND NOT EXISTS (
      SELECT 1 FROM storage s WHERE s.history_id = h.id
    );
$$;
```

### Storytelling 13-day cutoff

Storytelling rows hide from the UI 1 day earlier (existing logic at `history-grid.tsx:300-314`). The cleanup cron is independent of UI hiding — it runs on a 14-day cutoff for ALL types. The 1-day earlier UI cutoff for fairytale just gives the user a visual warning before the file actually disappears from B2.

If we wanted exact UI-DB parity, we'd add a per-type cutoff to the function. **Decision: 14-day cleanup for all types is fine** — saves a row of complexity, and the 1-day window where storytelling is hidden but file still exists doesn't hurt anything.

### Safety net

Modal cron failure modes:
- DB query fails → no deletes happen, retry next day. Storage grows ~5MB/user/day until fixed.
- B2 delete fails on individual row → log + continue with rest. Stale rows retried tomorrow.
- Modal scheduler down for multiple days → manual one-shot run via Modal CLI brings cleanup back in sync.

No B2 lifecycle rule. Saved-file metadata lives only in Supabase, and B2's prefix-based lifecycle can't conditionally skip "saved" files. We rely on the cron's `NOT EXISTS (storage row)` check.

## Schema change

```sql
-- Migration: 0009_b2_mirrored_at.sql
ALTER TABLE history ADD COLUMN b2_mirrored_at TIMESTAMPTZ;
CREATE INDEX history_b2_unsaved_idx
  ON history (created_at)
  WHERE b2_mirrored_at IS NOT NULL;

CREATE OR REPLACE FUNCTION history_unsaved_past_ttl() ... -- shown above
```

The new column:
- `NULL` = row not (yet) on B2 content bucket — either pre-this-feature or mirror failed
- `NOT NULL` = mirrored at this timestamp; output_url is on peninglab-content; eligible for cleanup if past TTL and no storage row

The partial index targets the cleanup query specifically; rows without `b2_mirrored_at` (the long tail of pre-feature data after backfill completes) are excluded.

## Backfill — admin canary first, then all users

Phase 1 ships with two backfill operations:

### Backfill 1: admin@gmail.com canary

```python
def backfill_user(user_id: str):
    rows = supabase.from_("history").select("*") \
        .eq("user_id", user_id) \
        .is_("b2_mirrored_at", None) \
        .in_("status", ["done"]) \
        .execute()
    
    for row in rows.data:
        if not row["output_url"]:
            continue
        if "peninglab-content" in row["output_url"]:
            # Already migrated somehow — fix up the timestamp
            supabase.update("history").set({"b2_mirrored_at": NOW()}).eq("id", row["id"])
            continue
        
        ext = derive_ext(row["type"], row["output_url"])
        key = f"users/{row['user_id']}/{row['type']}/{row['id']}.{ext}"
        public_url = f"{B2_CONTENT_PUBLIC_BASE}/{key}"
        
        try:
            mirror_to_content_bucket(
                source_url=row["output_url"],
                key=key,
                content_type=guess_mime(ext),
            )
            supabase.update("history").set({
                "output_url": public_url,
                "b2_mirrored_at": NOW(),
            }).eq("id", row["id"])
            log.info(f"backfilled {row['id']} -> {key}")
        except SourceUnreachable:
            # Provider URL already expired (likely past Crun 14-day TTL).
            # Skip — row is stale anyway, will be hidden by UI filter.
            log.info(f"skipped {row['id']} (source 404)")
        except Exception as e:
            log.warn(f"backfill failed for {row['id']}: {e}")
```

Run for `admin@gmail.com` first. Verify in dashboard:
- All UGC / Image / Storytelling cards still display
- Refresh = 0 network (browser cache)
- Save flow on a backfilled row works <100ms

### Backfill 2: all users

After admin canary verifies, same script with no user_id filter:

```python
backfill_all():
    rows = supabase.from_("history").select("*") \
        .is_("b2_mirrored_at", None) \
        .in_("status", ["done"]) \
        .order("created_at", desc=True) \
        .limit(BATCH_SIZE)
    # ... loop, batch, sleep between batches
```

Estimated: 1000 rows × ~5MB avg × ~2s download + upload = 30-60 minutes wall-clock. Run during low-traffic window (03:00 MYT).

Backfill is **idempotent** — re-running does nothing for already-mirrored rows.

## Self-review notes

**Spec coverage:** Every component (URL strategy, generation-time hook, Save flow, cleanup, schema, backfill) has a concrete section with code snippets where appropriate.

**Internal consistency check:**
- The cleanup query uses `b2_mirrored_at IS NOT NULL` — matches the column added in the schema migration ✅
- Save flow detects `peninglab-content` in URL — matches the pattern stored by Component 2 ✅
- Backfill skips rows already on `peninglab-content` — matches Component 2's URL pattern ✅
- 14-day cleanup vs 13-day storytelling UI cutoff: explicitly addressed in Component 4 — accepted 1-day window where row is hidden but file exists ✅

**Placeholder scan:** No "TBD" / "implement later" / "see other doc" — every section concrete.

**Scope check:** Single implementation plan. Four commits, each independently revertible. Cloudflare, JPG posters, account-level cache sync are explicitly non-goals.

**Ambiguity check:**
- "Mirror failure means…" → spec says fallback to provider URL, store error_message, leave `b2_mirrored_at` NULL so backfill retries. Not ambiguous.
- "Save on un-mirrored row" → spec says fall back to old download+upload flow. Not ambiguous.
- "Cleanup of saved row" → spec says `NOT EXISTS (storage row)` skips saved rows. Not ambiguous.
- "Provider URL already 404 during backfill" → spec says skip + log + don't update row. Not ambiguous.
- Storytelling 13-day vs 14-day → explicitly addressed; cleanup uses 14d for all types.

**Risk areas:**
- `lib/settle.ts` is the path every video flows through. Mistakes here affect all gens. Mitigated by best-effort design (mirror failure ≠ gen failure).
- Modal worker bucket swap. If misconfigured, storytelling videos break. Mitigated by deploying after settle.ts hook is verified working.
- Backfill at scale (~1000 rows). Risk of rate-limiting from providers. Mitigated by batch processing + sleep between batches + idempotent.

**Things explicitly NOT in this spec:**
- React.memo on HistoryCard (different concern: click-handler perf)
- SWR cache for history rows (different concern: API caching)
- Virtualized scrolling (UX choice, separate decision)
- JPG posters (separate optimization)
- Cloudflare CDN (Phase 2 — pure additive perf)

If client complains "first time loading is still slow on Malaysian connection", Phase 2 (CF) is the answer. If client complains "click Save feels laggy", this spec already fixes that.
